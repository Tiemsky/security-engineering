# ADR-0001 — Architecture of the security-engineering ecosystem

Status: accepted · Date: 2026-10-16

## Context
One security methodology must serve Claude Code, Google Antigravity and OpenCode, and Laravel + NestJS apps,
without three diverging copies. Verified facts (official docs, 2026-10-16) are in `docs/compatibility.md`.

## Decisions
1. **Canonical skill format** — `skills/<name>/SKILL.md`, Agent Skills format, frontmatter limited to
   `name` + `description` (+ `metadata` string map). `name` == directory, regex `^[a-z0-9]+(-[a-z0-9]+)*$`, ≤64 chars
   (strictest of the three tools = OpenCode). No tool-specific keys in canonical skills. Long references live in
   `skills/<name>/references/*.md`, linked by relative path.
2. **Agents** — one conceptual spec per agent in `agents/*.md` (role, mission, allowed capabilities, forbidden actions,
   skills). Native files in `adapters/<tool>/agents/` are *generated by hand-reviewed templates and checked by tests*
   for consistency (same name, same skill list, read-only agents have no write/edit capability).
   Antigravity custom subagents are a documented feature but their field validation is immature (misspelled tool name
   may hang) → tool names are the ones already used by a working local agent; marked *unverified at runtime*.
   Antigravity **workflows are deprecated (stop working 2026-10-19)** → not shipped; skills + rules are used instead.
3. **Global vs project** — GLOBAL installs skills + agents for the user. PROJECT installs a *minimal integration package*:
   `.security-engineering/config.yaml` (pinned version, framework, exceptions, verify commands) + tool instruction
   snippets. Skills are copied into the project only with `--vendor-skills` (team-shared pinned copy). Never the whole repo.
4. **Install mechanism** — copy (not symlink: Windows needs privileges/Developer Mode) with a manifest
   `.security-engineering.manifest.json` (version + sha256 per file). Update = compare manifest version/hash; files edited
   locally are detected and never overwritten without backup + `--force`. Idempotent. Dry-run everywhere.
5. **Versioning** — SemVer in `VERSION`; contracts carry their own `schema_version` with compat rules in `contracts/COMPATIBILITY.md`.
   Projects pin a version in `.security-engineering/config.yaml`; installer refuses a mismatched version unless `--allow-version-change`.
6. **Security/permission boundaries** — installer never edits permission allowlists, never enables bash broadly, never
   writes secrets. JSON configs are merged with a key-level merge that only *adds* our keys; backups `*.bak.<ts>` are made before any change
   to an existing file. Auditor/Reviewer agents are read-only by construction (tests enforce).
7. **Runtime vs methodology** — skills do not secure apps; they drive implementation. Runtime reference code lives in
   `adapters-runtime/` and must be wired into the real request path by the Implementer.
8. **Tooling** — Bash + PowerShell installers, Python 3 stdlib tests (PyYAML only for policies). No application runtime for distributing Markdown.
9. **Automated response** — deterministic rule engine, observe-only default; LLM output is never an enforcement authority.
