# security-engineering

An **agentic security toolkit**: one canonical methodology (skills + agent specs + contracts + policies) deployed natively into the AI coding agents **Claude Code**, **Google Antigravity** and **OpenCode**, backed by a **deterministic scope gate**, a **gate-driven active-testing executor**, and reference **observe-mode runtimes** for **Laravel** and **NestJS**.

> It is an engineering assistant, not an automatic guarantee. The AI agents *read code and implement/verify* protections; the executor *runs authorized active tests*; the runtime *emits events and detects abuse in observe mode*. Only the code that lands in your application, and the tests you run, secure it. What each part is verified to do is in [`docs/status.md`](docs/status.md) and [`docs/validation-v0.1.0.md`](docs/validation-v0.1.0.md).

---

## 1. The four layers

| Layer | What it is | Who drives it | Acts on the target? |
|---|---|---|---|
| **A. Agents + skills** | 5 AI agents loading 13 skills; audit, threat-model, implement, review | an AI coding tool (Claude Code / OpenCode / Antigravity) | reads code; the implementer writes code (on approval) — **no network** |
| **B. Scope gate** | `scripts/assessment-gate.py` — deterministic, no LLM | you / the agents / the executor | **never contacts a target**; only decides what is permitted |
| **C. Active-testing executor** | `scripts/pentest-runner.py` — 11 gated modules | you (a deterministic runner, not an agent) | sends requests to a target **only when the gate says `allow`** |
| **D. Observe-mode runtime** | Laravel + NestJS request instrumentation + decision engine | your application, in production | emits events, detects abuse; **observe-only** until you promote a rule |

A code audit (A) does not validate a deployed system; an active scan (C) does not prove the code is clean; the runtime (D) is what executes in production. They are related but distinct flows.

## 2. Layer A — the agents and their skills (AI-piloted)

Five agents, same names in every tool, with per-tool permissions in `agents/manifest.json` (native files are generated by `scripts/build-adapters.py`; never edit them by hand):

| Agent | Role | Can write? |
|---|---|---|
| `security-orchestrator` | sequences the workflow; **stage 0 = environment & scope** | no (delegates) |
| `security-architect` | discovery, threat model, plan | no |
| `security-auditor` | read-only audit, evidence, severity | no |
| `security-implementer` | implements an **approved** plan, with tests | yes |
| `security-reviewer` | independent validation in a fresh context | no source edits |

**13 skills** (the methodology modules the agents load; `skills/<name>/SKILL.md`, 11 mandatory sections each):

`environment-assessment` · `security-audit` · `threat-modeling` · `auth-hardening` · `api-security` · `rate-limiting` · `request-observability` · `bot-detection` · `audit-trail` · `devsecops` · `incident-response` · `security-validation` · `framework-adapter-development`

**How they are invoked** (the three tools do **not** share one syntax — full matrix in [`docs/COMMAND-REFERENCE.md`](docs/COMMAND-REFERENCE.md)):
- Claude Code: `claude --agent security-auditor` (the session *is* that agent).
- OpenCode: `opencode run --agent security-orchestrator "…"` (only the primary agent is selectable; it delegates).
- Antigravity: `agy --agent security-orchestrator -p "…"` (delegates via `invoke_subagent`).

Standard workflow:
```
Scope → Discover → Model → PLAN → (you approve) → Implement+tests → Review (fresh) → report: Implemented / Tested / Unverified
```
Copy-ready prompts: [`docs/EXAMPLES.md`](docs/EXAMPLES.md).

## 3. Layer B — the deterministic scope gate

`scripts/assessment-gate.py` decides, with no LLM and without touching any target, whether an activity is permitted:

- `classify SCOPE.yaml` → environment (`local` / `staging` / `production` / `unknown`) from **verifiable evidence only** (a hostname or URL is never evidence; reachability is never authorization; conflicting evidence ⇒ `unknown`).
- `check SCOPE.yaml --activity A --target T [--now ISO]` → `allow` (exit 0) / `needs_confirmation` (3) / `deny` (1).
- `validate-report REPORT.json` → schema + cross-field rules (a PASS needs evidence; a code audit cannot PASS an operational control; no report may call the app "secure").

Activity classes: `static_analysis`, `passive_observation`, `active_read_only`, `active_authenticated`, `active_fuzzing`, `active_load`, `active_state_changing`, `sensitive_data_collection`, and the two **always denied** classes `exploitation` and `enforcement_action`. Rate caps: **200 / 50 / 5** requests per second (local / staging / production). Scope template: `adapters/project/assessment-scope.yaml.template`.

## 4. Layer C — the active-testing executor (`pentest-runner.py`)

A deterministic runner — **not an agent, no LLM** — that performs active security tests against a target you own or are explicitly authorized to test. It is safe by construction and every property below is covered by tests in `tests/pilot/test_pentest_runner.py`:

- **Gate-first** — before each module it calls `assessment-gate.py check` for that module's activity class and runs it **only** on `allow`. A mutation test proves bypassing the gate breaks the "nothing is sent on deny" guarantee.
- **Non-destructive** — no `exploitation`/`enforcement_action` module exists (the gate denies both); every shipped module reads only and never follows with a state change.
- **Rate-bounded** — stdlib modules are paced in-process; external tools get the gate's cap via their own flag (`-rl`, `--delay`, `--max-rate`, `-rate`).
- **Secrets stay out** — a test-account credential comes from `$SE_AUTH_HEADER`, never the committed scope, and is never written to the log.
- **Clean skip** — a module whose binary is absent is skipped with a message; a gate-denied module sends nothing.

### Modules (11)
| Module | Activity | Needs | Checks |
|---|---|---|---|
| `http-headers` | active_read_only | stdlib | HSTS, CSP, X-Content-Type-Options, X-Frame-Options, Referrer-Policy |
| `cookie-flags` | active_read_only | stdlib | Set-Cookie Secure / HttpOnly / SameSite |
| `cors` | active_read_only | stdlib | reflected-origin / credentialed CORS |
| `tls` | active_read_only | stdlib | negotiated TLS version, certificate validity/expiry |
| `tls-scan` | active_read_only | `testssl.sh` | deep TLS scan (protocols, ciphers, cert) |
| `http-scan` | active_read_only | `nuclei` | template detection (no DAST, `-ni`, rate-capped) |
| `content-discovery` | active_read_only | `ffuf` | path discovery; flags exposed `.git`/`.env`/backup/admin |
| `port-scan` | active_read_only | `nmap` | exposed services (`-sT`, no scripts/`-A`/`-O`); flags data-store/insecure-remote ports |
| `injection-fuzz` | active_fuzzing (+ `--confirm`: sensitive_data_collection) | `sqlmap` | SQL-injection **detection**; optional benign proof (`--banner`/`--current-user`/`--current-db`). Dump/shell/enumeration permanently refused |
| `idor-bola` | active_authenticated | stdlib | object-level authz (IDOR/BOLA) with a dedicated test account |
| `priv-esc` | active_authenticated | stdlib | function-level authz / privilege escalation (BFLA) with a low-privilege test account |

```bash
scripts/pentest-runner.py list                                   # modules, activity class, required binaries
scripts/pentest-runner.py plan SCOPE.yaml --target URL           # gate decision per module; sends NOTHING
scripts/pentest-runner.py run  SCOPE.yaml --target URL --out DIR  # runs only the modules the gate allows
```
`exploitation` (dumping data, `--os-shell`, enumerating credentials) is **never** automated: it is `ALWAYS_DENIED` by the gate and stays a manual step you perform on a system you own. Full reference and per-tool flags: [`docs/ACTIVE-TESTING.md`](docs/ACTIVE-TESTING.md).

## 5. Layer D — the observe-mode runtime (backend only)

`adapters-runtime/{laravel,nestjs}` is a reference runtime wired into the **real backend request path** (Laravel `HttpAccessMiddleware`; NestJS `SecurityMiddleware` + `AccessInterceptor` + exception filter). It:

- resolves the client IP through trusted proxies (IPv4/IPv6, /64 aggregation) and assigns a request id;
- emits **structured, redacted** `http_access` events (method, **route template** — never the raw URL/query, status, duration, UA) and security/decision/outcome events;
- feeds a **deterministic `DecisionEngine`** that evaluates 7 shipped detection rules (credential stuffing, account spray, OTP brute force, sequential-id enumeration, 404 scanner bursts, honeypot hits, bad webhook signatures);
- can enforce (429 on an active IP/prefix) — **but ships in `observe` mode**: it records decisions and enforces nothing until you promote a rule through a controlled process.

**Honest scope:** this is **backend only — there is no frontend instrumentation.** "User activities / audit trail" is the `audit-trail` **skill** (guidance the agent implements in *your* application), not a shipped runtime component. State is per-process memory: no Redis, no workers; a restart loses windows and active blocks; `account_lock` / `session_revocation` / `challenge` are **never executed** (always routed to manual review). It is **not** installed by the agent installer — wire it per [`docs/project-integration.md`](docs/project-integration.md).

## 7. Install
```bash
# global (current user) — dry-run first
scripts/install.sh --mode global --dry-run
scripts/install.sh --mode global                 # tools auto-detected; or --tools claude,opencode,antigravity
scripts/validate-installation.sh --mode global   # static verification only

# per application: version-pinned integration package
scripts/install.sh --mode project --project-dir ~/dev/my-app --vendor-skills
scripts/validate-installation.sh --mode project --project-dir ~/dev/my-app
```
Windows: `scripts/install.ps1 -Mode global -DryRun`. Details: [`docs/installation.md`](docs/installation.md), [`docs/project-integration.md`](docs/project-integration.md). The installer copies files (no symlinks), never touches permission/settings files, and backs up conflicts with `--force`.

## 9. Safety invariants (hold across all layers)
- No LLM is an enforcement authority; a model never authorizes or overrides a security action.
- `exploitation` and `enforcement_action` (account lock, session revocation, IP/firewall block) are never initiated by an agent or the executor — a human owner does them through a controlled process.
- Active tests only on explicitly authorized targets, within a window, under request caps, with stop conditions; production is non-destructive by default (heavy activity needs a specific, attributed, unexpired exception).
- Read-only agents stay read-only (enforced by the tool's allow-list + `tests/agents`); the implementer changes only approved files; secrets are reported by path + type, never value.
- Detection/response ship in `observe`; promoting a rule is a separate, explicit, authorized step.

## 10. What this toolkit does NOT do (yet)
- No automated exploitation, data exfiltration or remote code execution (by design — see §9).
- No frontend instrumentation; the runtime is backend-only and observe-only.
- No persistence, correlation store, admin API, RBAC or supervision UI (the runtime emits events; it does not store, search or display them).
- No pilot beyond one read-only Laravel audit (pilot A); the active-testing executor has had **no real-target run** yet, only loopback-fixture tests.
- CI has never run on a hosted runner; actions are not SHA-pinned.
- Windows native and macOS are not executed. Full list: [`docs/status.md`](docs/status.md).
